# Controle de Estoque TI — WAP

Sistema interno para substituir o controle de ativos de TI feito hoje em três planilhas desconectadas (inventário, saída e devolução) + revisão por Gmail + relatório semanal manual por filial.

**Ideia central:** registra-se só a *movimentação* (saída, devolução, compra, transferência…) uma única vez; o estado do ativo, o estoque e os relatórios por filial derivam automaticamente por trigger no banco. O relatório deixa de ser enviado por e-mail — vira um link sempre atualizado, protegido por senha.

O sistema está **em produção desde o go-live de 15/07/2026** (1.596 ativos, 5 filiais). A entrada de dados do dia a dia é **100% manual** pelo sistema — não há sincronização com planilhas.

## Stack (decidida em 09/07/2026)

- **Next.js 16** (App Router, Turbopack) + **React 19** + **TypeScript strict**
- **Tailwind CSS v4** + **shadcn/ui** + **Recharts v3** (análise de alternativas em [`docs/PLANEJAMENTO.md`](docs/PLANEJAMENTO.md) §2.1)
- **Supabase** (plano Free) — Postgres, Auth (login por convite), RLS, Realtime, Storage
- Deploy: **Vercel** (conta Pro já paga — custo novo R$ 0 para a empresa)

**Regra de patrimônio:** o patrimônio identifica o equipamento, mas repete em casos raros — quem é único é o par **patrimônio + service tag** (spec §5, regra 1). Toda busca por patrimônio trata o caso de múltiplos resultados.

**Modelo de acesso (duas portas):** operar = login com conta corporativa (`@wap.ind.br`, `@stefanini.com` ou `@latam.stefanini.com`), com **quatro cargos em hierarquia — Desenvolvedor ⊃ Administrador ⊃ Operador ⊃ Consulta** (F21 acabou com o nível único; a F22 acrescentou o Desenvolvedor no topo): todo perfil ativo **lê** tudo, e o que se restringe é a **escrita** — operador escreve só nas filiais vinculadas, consulta não escreve nada, administrador alcança `/admin/**` e o import, e o Desenvolvedor ainda gerencia contas (e-mail, exclusão, sessões) e a área `/dev`. Visualizar relatórios = **senha de acesso, sem conta** (senhas com rótulo, criadas e revogadas individualmente) — é outra porta, não um cargo. Detalhes na spec §3, em [`docs/ADR-002-papeis-e-permissoes.md`](docs/ADR-002-papeis-e-permissoes.md) e em [`docs/ADR-001-rls-por-filial.md`](docs/ADR-001-rls-por-filial.md).

## Desenvolvimento local

Pré-requisitos: **Node 20+** e **npm**. Banco, Auth e Storage rodam num projeto **Supabase de desenvolvimento** — nunca produção.

1. `npm install`
2. Copie `.env.example` para `.env.local` e preencha com os valores do Supabase **de DEV**.
3. `npm run dev` → app em `http://localhost:3000`.

Variáveis de ambiente (todas em `.env.example`): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (só server-side/scripts — nunca `NEXT_PUBLIC`), `VIEW_SESSION_SECRET` (assina o cookie da sessão de visualização por senha) e as guardas `SEED_CONFIRM`/`SEED_PROJECT_REF`, que impedem os scripts de dados fictícios de rodarem fora do DEV.

### Comandos

| Comando | O quê faz |
|---|---|
| `npm run dev` / `npm run build` / `npm run lint` | Desenvolvimento · build de produção · lint (verificação obrigatória ao fim de cada ordem) |
| `npm run test` | Vitest — testes de funções puras (normalização de patrimônio, De→Para, datas, motor do import…) |
| `npm run db:seed` | Popula o banco de DEV com dados fictícios determinísticos (100% fictícios — jamais aponta para produção) |
| `npm run db:reset` | Zera as tabelas de dados (exige as guardas do `.env.local`) |
| `npm run db:types` | Regenera `src/lib/types/database.ts` a partir do schema |
| `npm run carga` | Carga única do go-live (`scripts/import/`; guardas `CARGA_*`) — ferramenta, não feature |

O CI (`.github/workflows/ci.yml`) roda em todo push na `main` e em qualquer PR: um job de `lint + test + build` e um job de **banco** que sobe um Postgres, aplica **todas as migrations** em ordem e roda os roteiros de `supabase/tests/`.

A regra mora no Postgres, não na tela: oito migrations (`0061`–`0068`) trocaram **todas** as policies de escrita, puseram a guarda de administrador **dentro** da RPC do import (que é `security definer` e passa por fora de qualquer policy), fecharam os buckets de Storage por cargo e travaram a auto-promoção por **grant de coluna** — o advisor `rls_policy_always_true` saiu de **12 para 0**. A revisão adversarial da própria fase achou, **e reproduziu**, um furo que furava a fase inteira: a policy de movimentações gateava a filial que o **cliente declara**, e um operador vinculado a uma filial conseguia mover para si um ativo de outra mentindo um campo — corrigido na `0067`, que passou a gatear a filial de **origem lida do banco**. O roteiro de RLS foi de 41 para **47 asserções** (as novas são exatamente a lacuna que deixou o furo passar) e roda verde nos dois bancos. O deploy foi um **não-evento** por construção: o backfill marcou todos os usuários atuais como Administrador com todas as filiais, e o smoke do app antigo contra o banco novo deu **86 OK · 0 falha**. **Zero dependência nova.** **1.588 testes** (eram 1.496). Decisão em [`docs/ADR-002-papeis-e-permissoes.md`](docs/ADR-002-papeis-e-permissoes.md); evidências, roteiro manual de 5 minutos e "o que este relatório NÃO prova" em [`docs/RELATORIO-F21.md`](docs/RELATORIO-F21.md).

A **F22** pôs um quarto cargo no **topo** da hierarquia — **Desenvolvedor ⊃ Administrador ⊃ Operador ⊃ Consulta** — porque a F21 tinha deixado o topo achatado: um administrador rebaixava, desligava e apagaria qualquer pessoa, **inclusive quem mantém o sistema**. Agora ninguém abaixo de Desenvolvedor altera, desativa, apaga ou promove quem é Desenvolvedor, e essa recusa mora no banco (um trigger que barra **até o service role**), não na tela. Junto veio a gestão de conta que só existia no painel do Supabase — **trocar o e-mail de login, apagar uma conta e encerrar as sessões de alguém** —, tudo com trilha em `eventos_admin`, mais a área **`/dev`** (diagnóstico do que está no ar, migration aplicada × repositório, **sete checagens de integridade só-leitura**, auditoria completa com export e manutenção; **sem console de SQL**, de propósito). **Apagar preserva a história:** a conta some do login para sempre e o e-mail volta a ficar livre, mas o perfil é **arquivado** e cada movimentação, termo e evento continua mostrando o nome de quem o fez — o caminho ingênuo era impossível, porque dez FKs de histórico bloqueiam e o cascade para o Auth fazia `deleteUser()` falhar. Uma oitava checagem de integridade foi **descartada com número**: acusou 1009 de 1231 ativos em produção e a investigação mostrou artefato de ordenação, não inconsistência. As sete migrations do desenho (`0071`–`0077`) foram aplicadas em ensaio e produção — mais a `0078`, também aplicada nos dois, que a leitura de advisors depois do apply pediu (duas funções auxiliares saíram da API pública) —, com **zero dependência nova**. Emenda de arquitetura no §13 de [`docs/ADR-002-papeis-e-permissoes.md`](docs/ADR-002-papeis-e-permissoes.md); evidências e "o que este relatório NÃO prova" em [`docs/RELATORIO-F22.md`](docs/RELATORIO-F22.md).

A **F23** deu ao Desenvolvedor as ferramentas **destrutivas** que faltavam — apagar um ativo com todo o rastro, apagar a última movimentação, apagar um item com os lançamentos, resetar o acervo ou os lançamentos de uma filial (ou de tudo), e forçar o estado de um ativo ou o saldo de um item —, todas numa **Zona destrutiva** própria (`/dev/destrutivo`), com confirmação digitada, justificativa obrigatória, backup e trilha. Mas o achado que reorientou a fase foi outro: a ordem mandava **preservar** a garantia de que ninguém apaga movimentação por fora, e a medição mostrou que **essa garantia não existia** — a "imutabilidade" era só a *ausência* de policy de UPDATE/DELETE, o que segura o cargo `authenticated` e **não segura o service role** (que ignora RLS e tinha grants amplos de tabela). Foi preciso construí-la: um **trigger** que recusa por padrão e só deixa passar por uma janela que as RPCs oficiais abrem e fecham — provado **em produção**, como service role, com todas as tentativas de apagar/alterar devolvendo 42501 e o INSERT legítimo continuando a passar. A prova também encontrou um defeito real: `created_at` é o mesmo instante para linhas gravadas na mesma transação, então "a última movimentação" de um ativo importado saía de um **sorteio de uuid** — e apagar a errada restaurava o ativo do snapshot anterior ao próprio nascimento; medido em **1111 dos 1232 ativos** de produção, corrigido recusando o empate em vez de eleger um desempate. **Doze migrations (`0079`–`0090`)** em ensaio e produção, **zero dependência nova**, **nada do acervo tocado** (a fase instala as ferramentas; usá-las é decisão do dev). **1.667 testes** e um roteiro SQL de **108 asserções**. A **F24** tirou do caminho o último bloqueio herdado do go-live: uma linha do CSV cujo par patrimônio+service tag já existia em **outra filial** travava o import inteiro, e a única saída era remover a linha. Agora ela **importa** — a identidade do ativo passou a ser **por filial** (dentro da filial a duplicata segue impossível; entre filiais, o par pode existir) — e o duplicado vira a pendência **"conflito entre filiais"**, com uma **mesa** própria em `/pendencias` que mostra os dois cadastros **lado a lado**, realça os campos que divergem e traz o histórico de cada lado (inclusive quantas movimentações são **de verdade**, e não da carga do import). De lá o **administrador** apaga o cadastro errado — um, vários ou ambos —, e essa é a **única exclusão de ativo fora da Zona destrutiva do dev**: a RPC alcança exclusivamente ativo que esteja em conflito **naquele instante**, trava os **dois lados** antes de revalidar (para o gêmeo não sumir no meio) e recusa a operação **inteira** se um único id estiver fora. O que o import **não** faz continua igual: ele não move equipamento de filial. A auditoria que a ordem mandou fazer encontrou um furo real — corrigir patrimônio e definir service tag na ficha dependiam **inteiramente** do índice global e passariam a abrir conflito em silêncio; as duas ganharam a checagem explícita. **Oito migrations (`0091`–`0098`)** em ensaio e produção — a última nasceu da revisão adversarial, que confirmou quatro achados entre dezenove —, **zero dependência nova**, **nada do acervo tocado** (1.232 ativos e 2.377 movimentações antes e depois). **1.697 testes**, um roteiro SQL novo de **38 asserções** e smoke pós-deploy **89 OK · 0 falha**. ## Como as fases funcionam

As ordens rodam em **modo autônomo com acesso total** (decisão de 09/07/2026, regras no [`CLAUDE.md`](CLAUDE.md)): o Claude executa tudo — decisões, merge, deploy e produção — sem pedir autorização, compensando com autoproteções (backup/dry-run em operação destrutiva) e rastro auditável em [`docs/DECISOES.md`](docs/DECISOES.md). Cada fase é uma ordem de serviço em [`docs/prompts/`](docs/prompts/); só se executa a ordem que o Johnny colar na conversa.

O sistema **não nasce com os dados reais**. O desenvolvimento roda com dados fictícios; os dados reais entram por **carga de go-live**: a carga global inicial pelos scripts da F4 (autônoma, na janela do go-live) e, desde a F7, o **import de startup por filial** pela tela `admin/importar` (só *Substituir tudo*, go-live novo de uma filial — spec §10.2). A entrada do dia a dia continua 100% manual — ser mais prático que o Excel é o requisito central.
